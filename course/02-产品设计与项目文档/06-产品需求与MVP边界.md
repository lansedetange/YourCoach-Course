# 第 6 阶段：产品需求与 MVP 边界

### 本课目标

把“想做一个私教预约平台”的想法收敛为可验证的第一版需求：明确谁使用、解决什么问题、第一版必须完成什么，以及哪些功能明确不做。

### 你将完成

1. 一份填写完成的 `docs/PRODUCT.md` 初稿。
2. 一份写入 `docs/SPEC.md` 的 MVP 功能清单、业务规则和排除项。
3. 一个能约束后续页面、数据库、云函数和 Codex 修改范围的最小预约闭环。

### 前置条件

1. 已完成第 05 课，能在课程仓库运行 `git status --short` 和 `node scripts/audit-course.mjs`。
2. 已阅读 `README.md`、`AGENTS.md`、`docs/PRODUCT.md` 和 `docs/SPEC.md` 的模板。
3. 当前只讨论第一版；不要把未来设想当作本课必须实现的需求。

### 核心概念

- **MVP（最小可行产品）**：能让真实目标用户完成核心任务、并验证需求是否成立的最小版本，不是功能最少的演示页。
- **用户故事**：用“谁，在什么场景，想完成什么，因此得到什么结果”描述需求，例如“用户在同城寻找私教时，想查看可约时段，因此能选择合适课程”。
- **验收标准**：不用猜测的完成条件；例如“同一教练同一时段不能存在两笔有效订单”。
- **范围蔓延**：没有评估就持续加入功能，导致项目无法测试或上线。MVP 用明确的“不做清单”阻止它。

### 本课范围

本课只产出产品文档，不设计界面、不建数据库、不写小程序页面、不调用云函数、不申请支付。第一版只支持同城、线下到店、一对一私教服务；真实微信支付会在第 24 课处理，本阶段只把模拟支付列为流程验证手段。

### 关键决策

课程默认采用“先跑通单一预约闭环，再扩展”的方案。

```text
用户选教练、场馆、时段
          ↓
创建一笔待支付预约
          ↓
模拟支付并等待教练确认
          ↓
到店核销、完课、评价
          ↓
平台计算教练收益
```

第一版的取舍：

- 必做：用户查找教练、选择场馆和时段、预约、模拟支付、教练确认、核销、完课、评价、后台审核。
- 暂不做：教练上门、团课、直播、社区动态、复杂即时聊天、会员体系、优惠券、营销裂变、跨城服务。
- 原因：这些暂不做项会引入路线、多人容量、内容审核、实时通信或复杂结算，不能帮助验证“同城线下私教预约”是否成立。

### 操作前检查

1. 在课程仓库根目录运行 `git status --short`，确认你知道现有改动来自哪里；不要删除别人的改动。
2. 打开 `docs/PRODUCT.md` 和 `docs/SPEC.md`，只在本课要求的章节填写内容。
3. 准备一个具体但虚构的样例：例如“用户在同一城市预约某位教练在某个合作场馆的一节课”。不要使用真实姓名、手机号、身份证、地址或订单信息。
4. 先接受一个限制：本课任何功能如果不能服务于上述预约闭环，就默认放进“以后再做”。

### 步骤 1

填写产品目标、角色和问题边界。

1. 打开 `docs/PRODUCT.md`，在“产品一句话”部分写下：这是一个撮合本地用户与健身私教进行线下到店一对一预约的平台。
2. 在“目标用户”部分分别写出三种角色：
   - 普通用户：寻找教练、选择场馆和时段、预约和评价。
   - 私教：提交入驻资料、管理价格与可约时间、确认订单、核销并查看收益。
   - 管理员：审核教练、维护基础信息、处理订单、退款和提现申请。
3. 在“第一版要验证的问题”部分写下：用户是否愿意在小程序中完成选择教练、场馆和时段并提交预约；教练是否能及时确认并履约。
4. 在“第一版不承诺”部分写下增长、社交、复杂营销和自动化运营不是当前目标。
5. 预期结果：任何同学读完这四段，能区分用户端、私教端、管理后台的职责，且知道平台不是健身内容社区。

可参考下面的文档片段；它写在 `docs/PRODUCT.md`，不是小程序代码：

```markdown
## MVP 一句话

让同城用户选择教练、合作场馆和可约时段，完成线下到店一对一课程预约。

## 不做清单

- 不支持教练上门、团课、直播和社区动态。
- 不支持复杂即时聊天；必要通知使用订阅消息。
- 不把真实支付、退款或提现判断放在前端。
```

### 步骤 2

把核心预约闭环写成可检查的用户故事和端职责。

1. 打开 `docs/SPEC.md`，增加“核心闭环”小节，按下面顺序写出流程：登录 → 浏览教练 → 选择场馆 → 选择时段 → 创建订单 → 模拟支付 → 教练确认 → 到店核销 → 完课 → 评价 → 计算收益。
2. 对每一步补一条用户故事和可观察结果。例如：“用户选择时段后，系统只展示该教练仍可预约的时段”。
3. 为三个端分配责任：用户端只能发起请求和展示结果；私教端只能处理属于自己的订单；后台只做审核、配置和运营处理；敏感状态由云函数在后端变更。
4. 标记本轮支付为“模拟支付”。写明它只用于验证订单流转，不能当作真实收款成功的证据。
5. 预期结果：流程中没有“前端直接把订单改成已支付/已完成”的步骤，也没有一个功能同时由三个端随意修改。

### 步骤 3

写下不能妥协的 MVP 业务规则与排除项。

1. 在 `docs/SPEC.md` 的“业务规则”小节加入以下规则，并把它们标为后续数据库、云函数和测试必须遵守的约束：
   - 只提供同城、线下到店的一对一服务。
   - 一个教练第一版只有一个主营项目，但可绑定多个合作场馆。
   - 用户预约必须选择具体场馆和具体时间段。
   - 同一教练同一时间段只能有一笔有效订单。
   - 金额一律保存为整数“分”。
   - 订单、支付、退款、核销、收益等敏感状态只能由后端变更。
   - 第一阶段使用模拟支付；真实微信支付、退款回调和对账在后续课程接入。
2. 在“不做清单”中写下暂不支持的功能，并在每项后标注原因。例如“团课：需要容量、多人支付和多人核销规则，超出一对一预约验证范围”。
3. 对每一项“想加的功能”问两个问题：它是否阻止用户完成预约？没有它能否验证核心闭环？两个答案都是否定时，放入以后再做。
4. 预期结果：任何新功能都能被归类为“当前必做”“后续候选”或“明确不做”，而不是停留在聊天记录里。

### 步骤 4

进行一次范围评审，并让 Codex 只审阅文档。

1. 用下面四个问题逐项审阅 `docs/PRODUCT.md` 和 `docs/SPEC.md`：
   - 普通用户能否完成一次预约？
   - 教练能否确认并完成一次课程？
   - 管理员能否审核教练并查看订单？
   - 每个敏感状态是否只允许后端变更？
2. 如果某个功能不能回答以上任一问题，把它移到“以后再做”，不要为它新建页面或数据表。
3. 把本课下方的 Codex 提示词发给 Codex；先让它列出歧义和风险，确认范围后才允许它修改 `docs/PRODUCT.md` 或 `docs/SPEC.md`。
4. 在课程仓库根目录执行：

```bash
git diff -- docs/PRODUCT.md docs/SPEC.md
node scripts/audit-course.mjs
```

5. 预期结果：diff 只出现产品文档的最小修改；课程审计通过。若 Codex 提议页面、数据库、支付或云函数实现，记录为后续课程任务，不在本课执行。

### 常见问题

- **把所有功能都写成 P0**：P0 应是“没有它就无法验证预约闭环”。将优惠券、直播、社区等移到后续候选。
- **只写“用户可预约”**：缺少场馆、时段、冲突和订单状态等可验收条件。补充谁、在哪、何时、成功后状态是什么。
- **把支付成功当成前端弹窗**：前端只能展示结果；真实支付成功必须由后端回调、验签和查询确认。当前只能写模拟支付。
- **同一规则在多个文件写出不同版本**：以 `docs/SPEC.md` 的业务规则为唯一来源；后续的流程、数据模型和测试都引用它。
- **让 Codex 从一句话生成整个项目**：这会绕过范围评审。要求它先读文档、列出假设、只改指定文件并给出检查结果。

### 安全与合规

产品文档不能包含真实教练资料、用户数据、商户信息、AppID、密钥、证书或生产环境标识。示例人物、城市、场馆和订单均使用虚构内容。

本课的边界不是微信平台资格结论。小程序类目、支付、备案、审核和隐私要求会变化，执行时请以微信公众平台当前页面和官方文档为准。
