# 第 7 阶段：用户流程与页面结构

### 本课目标

把第 06 课定义的预约闭环拆成用户、教练、管理员三条可检查的流程，并为每一步指定页面、可执行动作和状态归属。

### 你将完成

1. 更新 `docs/USER_FLOWS.md`，包含核心流程和异常流程。
2. 更新 `docs/PAGE_MAP.md`，列出三端页面、进入条件和离开条件。
3. 一份“谁能做什么”的动作清单，供第 19 课订单状态机和第 20–22 课页面开发使用。

### 前置条件

1. 已完成第 06 课，`docs/PRODUCT.md` 和 `docs/SPEC.md` 已明确 MVP 范围。
2. 知道用户端、私教端和管理后台不是同一套权限。
3. 不在本课创建 WXML、WXSS、TypeScript、Next.js 页面或数据库集合。

### 核心概念

- **流程**：一个角色为达成目标而经过的一串动作和系统结果。
- **页面结构**：把流程中的每个需要人确认、输入或查看结果的节点映射到页面。
- **状态归属**：某个状态由谁发起、由谁最终确认、由哪里保存。订单状态的最终确认必须在后端。
- **异常流程**：支付取消、时段被抢、教练拒绝、网络中断等非理想情况；它们和正常流程同样需要设计。

### 本课范围

只写流程和页面地图。页面视觉、交互稿在第 08 课处理；字段、集合和索引在第 12–13 课处理；订单的允许状态流转在第 19 课处理。本课不把“页面跳转”误当成“订单状态已成功改变”。

### 关键决策

先以一个用户的一节课为主线，再补关键异常，而不是先罗列页面。

```text
用户：发现教练 → 选择场馆/时段 → 提交预约 → 查看结果
                                      ↓
后端：校验身份、时段与金额 → 创建/变更订单 → 记录日志
                                      ↓
教练：确认或拒绝 → 核销 → 完课
                                      ↓
用户：评价              管理员：审核与异常处理
```

### 操作前检查

1. 打开 `docs/PRODUCT.md`、`docs/SPEC.md`、`docs/USER_FLOWS.md` 和 `docs/PAGE_MAP.md`。
2. 选用虚构样例，例如“用户预约一位教练在合作场馆的一个 60 分钟时段”；不要填真实资料。
3. 准备三种标记：用户操作、后端确认、只读展示。任何敏感状态都不能只标为“用户操作”。

### 步骤 1

编写用户端正常流程。

1. 在 `docs/USER_FLOWS.md` 新建“用户预约一节课”小节。
2. 依次写：微信登录 → 选择城市 → 浏览/筛选教练 → 查看详情 → 选择场馆 → 选择可约时段 → 确认信息 → 创建订单 → 模拟支付 → 等待教练确认 → 查看核销码 → 完课后评价。
3. 每一步写清“用户在哪个页面做什么”“后端需要校验什么”“下一步显示什么”。
4. 对“创建订单”和“模拟支付”标注：前端只能请求后端，不能自行写入 PAID、CONFIRMED、COMPLETED 等状态。
5. 预期结果：读者能从流程直接画出用户端页面顺序，且知道每次点击后的真实确认点。

示例格式：

```markdown
| 节点 | 用户端页面与动作 | 后端确认 | 下一步 |
| --- | --- | --- | --- |
| 选择时段 | 在教练详情页点选场馆和时段 | 检查时段仍可约 | 进入预约确认页 |
| 创建订单 | 点击“提交预约”一次 | 原子校验时段、金额和身份，写订单日志 | 返回待支付订单 |
```

### 步骤 2

编写教练端、后台流程和页面地图。

1. 在 `docs/USER_FLOWS.md` 写“教练履约流程”：登录 → 申请入驻 → 等待审核 → 配置资料/场馆/价格/排期 → 查看待处理订单 → 确认或拒绝 → 到店核销 → 标记完课 → 查看收益。
2. 写“管理员运营流程”：管理员登录 → 审核教练资质 → 维护场馆/项目 → 查看订单 → 处理退款、投诉、提现 → 查看操作日志。
3. 在 `docs/PAGE_MAP.md` 按三端分组列出页面；每个页面至少写“进入条件、主操作、离开或结果”。
4. 明确页面权限：用户不能进入教练工作台；教练不能查看他人订单；管理员操作需记录日志。
5. 预期结果：任何页面都能回答“谁能进入、看到什么、发起什么请求、成功后去哪里”。

### 步骤 3

补齐异常流程和返回策略。

1. 为以下情形各写一段流程：未支付超时、两个用户抢同一时段、用户重复点击提交、教练拒绝、用户取消、支付成功但页面关闭、核销码错误、网络恢复后重新进入。
2. 每段都写出“用户看到的提示”“后端最终依据”“订单不应变成什么状态”。
3. 规定重复提交的界面行为：按钮进入提交中状态，但真正的幂等判断由后端的请求标识或订单规则完成。
4. 规定网络中断后的行为：重新从后端读取订单详情，不根据本地页面猜测支付或确认结果。
5. 预期结果：异常不再由临时弹窗掩盖，后续测试能直接逐项验证。

### 步骤 4

做流程走查并限制 Codex 修改范围。

1. 找一位同学或使用本课提示词，让对方从“首次打开用户端”开始逐步朗读流程；每出现“然后就成功了”，追问由谁确认、保存在哪里。
2. 检查每个订单动作是否有发起端、后端确认和结果页。
3. 在仓库根目录运行：

```bash
git diff -- docs/USER_FLOWS.md docs/PAGE_MAP.md
node scripts/audit-course.mjs
```

4. 预期结果：只出现流程和页面地图的文档改动，课程审计通过；任何尚未决定的业务规则明确标为“待第 19 课确认”。

### 常见问题

- **先列菜单再补流程**：会得到孤立页面。先写用户目标和状态变化，再映射页面。
- **把“支付完成页”当支付成功**：页面只是展示；支付状态以后端回调、查询和订单详情为准。
- **教练确认后用户端不刷新**：流程必须写明用户重新进入订单详情时向后端读取最新状态。
- **异常只写一句“提示失败”**：需要补充原状态、禁止状态和可重试条件。
- **后台拥有所有权力但没有日志**：审核、退款、提现等后台动作必须写入操作日志，后续才能追踪。

### 安全与合规

流程文档使用角色和虚构样例，不记录真实订单、用户、教练资料或定位。订单、支付、退款、核销、收益的最终状态只能由后端变更，前端页面只显示后端结果。订阅消息、定位授权和隐私说明将在后续课程单独处理。执行时请以微信公众平台当前页面和官方文档为准。

### Codex 提示词

```text
角色：你是谨慎的微信小程序产品流程审阅者。
任务：只审阅并补充 docs/USER_FLOWS.md 与 docs/PAGE_MAP.md；先列出流程缺口和最小修改计划，得到确认后才改文档。
上下文：同城线下到店一对一私教预约平台，有用户端、私教端和 PC 管理后台。用户选择教练、场馆、时段后创建订单；订单、支付、退款、核销和收益由后端确认；同一教练同一时段仅一笔有效订单。
允许范围：只读取 README.md、AGENTS.md、docs/PRODUCT.md、docs/SPEC.md、docs/USER_FLOWS.md、docs/PAGE_MAP.md 和本课文件；只修改 docs/USER_FLOWS.md 与 docs/PAGE_MAP.md。
禁止范围：不得创建页面、数据库、云函数、支付配置、云环境或测试数据；不得改 Git 历史、添加依赖、发布或上传文件。
功能要求：为用户、教练、管理员分别写正常与关键异常流程；每个订单动作写明发起端、后端确认和结果页面；标明权限边界。
安全要求：不得输出或写入真实用户、订单、定位、AppID、密钥、证书或生产环境信息；不允许前端直接修改敏感订单状态。
测试要求：只运行 node scripts/audit-course.mjs 与只读 Git 命令；报告实际结果和未执行原因，不伪造流程测试。
验收要求：流程和页面地图足以支撑后续原型、订单状态机和三端开发，并覆盖至少八种关键异常。
报告要求：列出已读与修改文件、每项流程缺口、验证命令结果、遗留歧义和下一课建议；不要自行提交或推送。
```
