# 第 8 阶段：UI 与交互原型设计

### 本课目标

把页面地图转换为可实施的低保真原型说明：每页先解决用户目标、信息优先级和状态反馈，再讨论视觉风格。

### 你将完成

1. `docs/PAGE_MAP.md` 中关键页面的内容区、主操作和状态说明。
2. 一套覆盖用户端、教练端、后台的低保真原型清单。
3. 关键交互的加载、空、错误、权限和完成状态规则。

### 前置条件

1. 已完成第 07 课，三端流程和页面进入条件已经明确。
2. 已准备纸笔、白板或任意原型工具；本课不要求购买设计软件。
3. 只使用虚构姓名、图片占位、场馆和订单数据。

### 核心概念

- **低保真原型**：用方框、文字和连线表达内容与操作，不追求颜色、图片或像素级效果。
- **主操作**：当前页面最重要、最应该被完成的一项操作，例如预约确认页的“提交预约”。
- **状态页**：同一页面在加载、没有数据、出错、无权限或成功后的不同表现。
- **交互反馈**：点击后告诉用户系统正在做什么、成功还是失败，防止重复提交和误解。

### 本课范围

只定义信息结构、交互与状态，产出文档或原型链接说明。不要编写 WXML、WXSS、TypeScript、React 组件，也不要采购图片或确定最终品牌视觉。第 20–22 课才会把原型落实为三端页面。

### 关键决策

每个关键页面先回答四个问题：用户为什么来到这里、必须看到什么、只能做什么、失败或没有数据时怎么办。

```text
页面目标 → 信息优先级 → 主操作 → 状态反馈 → 返回流程走查
```

用户端优先完成预约；教练端优先处理待办和履约；后台优先审核、检索和留痕。不要为了“看起来完整”给每页塞入所有功能。

### 操作前检查

1. 打开 `docs/USER_FLOWS.md`、`docs/PAGE_MAP.md` 和 `docs/PRODUCT.md`。
2. 选出第一轮必须画的页面：用户首页、教练列表/详情、预约确认、订单详情；教练工作台、订单处理、核销；后台登录、教练审核、订单列表。
3. 为每个页面准备五行说明：目标、信息、主操作、不可操作项、异常状态。
4. 不在原型中填真实价格、定位、照片、用户资料、AppID 或订单号。

### 步骤 1

画出用户端核心页面的低保真原型。

1. 在 `docs/PAGE_MAP.md` 中为用户首页写“城市入口、推荐教练、筛选入口、订单入口”，并标明首页不显示后台或教练经营数据。
2. 为教练详情页画出从上到下的信息顺序：教练介绍 → 主营项目/服务价格 → 合作场馆 → 可约日期与时段 → 收藏/预约操作。
3. 为预约确认页只保留教练、场馆、时段、价格、取消规则说明和一个提交按钮；提交后按钮进入“提交中”，不可连续点击。
4. 为订单详情页按状态显示不同主操作，例如待支付显示继续支付/取消，待确认显示等待，待核销显示核销码；页面不能直接显示“已完成”按钮。
5. 预期结果：一个不了解项目的人可从原型看出如何完成预约，以及何时需要等待后端或教练确认。

### 步骤 2

画出教练端和后台的任务型页面。

1. 教练工作台首屏只展示待处理订单、今日课程、排期提醒和收益摘要；将资料、场馆、价格等管理功能放入二级入口。
2. 教练订单详情必须同时显示用户预约信息、确认/拒绝条件、当前状态和后端返回的操作结果；拒绝需要理由输入和二次确认说明。
3. 核销页以“扫描/输入核销码 → 后端验证 → 显示结果”为主线；不要在本地页面把订单改为已核销。
4. 后台审核页按“待审核资料、证书查看、通过/驳回、操作日志”排列；管理员没有理由删除已发生订单。
5. 预期结果：教练和管理员打开页面时能优先看到待办，而不是用户端的信息流。

### 步骤 3

为每个关键页面补齐状态和可访问性。

1. 在页面说明中写加载态：首次请求时显示骨架或明确加载文案，主提交按钮不可重复触发。
2. 写空态：没有教练、没有时段、没有订单、没有待审核资料时，解释原因并给出一个返回或刷新动作。
3. 写错误态：请求失败时显示可理解的错误和重试入口，不把后端错误堆栈展示给用户。
4. 写权限态：未登录先引导登录；未审核教练不能进入履约操作；无管理员权限不能进入后台页面。
5. 检查文字可读性：状态不能只靠颜色区分；按钮要有文字；重要操作应有确认提示。
6. 预期结果：原型包含正常页面之外的状态页，后续开发不会只实现“有数据且网络正常”的画面。

### 步骤 4

走查原型并用 Codex 做文档审阅。

1. 按第 07 课的三端流程逐页走查，确认每一个流程节点都有页面或明确的后台结果。
2. 检查每个页面只有一个明显主操作；若两个操作同样重要，拆为两个页面或由状态决定。
3. 使用本课提示词让 Codex 审阅文档，而不是让它直接生成 UI 代码。
4. 在仓库根目录运行：

```bash
git diff -- docs/PAGE_MAP.md
node scripts/audit-course.mjs
```

5. 预期结果：只出现页面地图或原型说明的变更，审计通过；视觉细节和代码任务留给后续课程。

### 常见问题

- **原型只有漂亮首页**：预约、等待、核销、失败等关键节点缺失。按流程补齐状态页。
- **一个页面有多个主按钮**：用户不知道先做什么。保留一个主操作，其余降级为次要入口。
- **空态只写“暂无数据”**：要说明没有什么、为什么可能没有、用户接下来可以做什么。
- **教练端复用用户端页面**：角色目标不同；教练端应该优先待办和履约。
- **先写代码再确认原型**：返工成本更高。先走查低保真原型，确认后再开发。

### 安全与合规

原型只能使用占位图和虚构内容，不能截图传播真实用户、教练证书、定位或订单。权限页面不得依赖“把入口隐藏起来”；后端仍必须校验身份和权限。涉及定位、手机号、订阅消息等授权说明将在对应课程处理。执行时请以微信公众平台当前页面和官方文档为准。

### Codex 提示词

```text
角色：你是谨慎的移动端产品设计审阅者。
任务：只审阅 docs/PAGE_MAP.md 中的低保真原型说明和状态规则；先给出缺口与最小计划，确认后才修改文档。
上下文：同城线下到店一对一私教预约平台有用户端、教练端和后台。订单、支付、退款、核销和收益由后端确认；前端只请求并展示结果。
允许范围：只读取 README.md、AGENTS.md、docs/PRODUCT.md、docs/USER_FLOWS.md、docs/PAGE_MAP.md 和本课文件；只可修改 docs/PAGE_MAP.md。
禁止范围：不得创建前端代码、设计资产、数据库、云函数、支付配置或真实原型链接；不得添加依赖、发布、上传或改 Git 历史。
功能要求：为关键页面补充目标、信息层级、一个主操作、加载/空/错误/权限状态和返回路径；保持 MVP 范围。
安全要求：不得使用或输出真实用户、教练、场馆、定位、订单、AppID、密钥或证书；不得以隐藏入口代替权限控制。
测试要求：只运行 node scripts/audit-course.mjs 与只读 Git 命令；报告真实结果和未执行原因。
验收要求：三端关键流程均有可实施的页面说明，且每个敏感状态的结果来自后端。
报告要求：列出已读与修改文件、发现的状态缺口、验证结果、遗留设计决策和下一课建议；不要自行提交或推送。
```
