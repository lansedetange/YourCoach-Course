# 第 9 阶段：Git、GitHub 与项目管理

### 本课目标

建立“小任务、可审阅、可回退”的协作习惯：每次让 Codex 或自己改动前先看范围，改动后看 diff，通过检查后再提交。

### 你将完成

1. 一套分支、提交信息和任务记录约定。
2. 能独立查看状态、差异、历史，并在不丢失文件的情况下撤回未提交改动。
3. 一份针对 Codex 的安全协作提示词。

### 前置条件

1. 已完成第 05 课，终端中的 `git --version` 可用。
2. 已有本地课程仓库；如使用 GitHub，已在官方页面完成自己的登录。
3. 当前工作区没有你不理解的改动；有改动时先记录来源，不删除。

### 核心概念

- **工作区**：电脑中正在编辑的文件。
- **暂存区**：准备进入下一次提交的文件清单；`git add` 只选择确认过的文件。
- **提交（commit）**：一个可说明、可回看的改动快照。
- **分支**：从稳定版本分出的独立工作线；一项功能或一组相关文档使用一个分支。
- **diff**：两份版本之间的逐行差异，是检查 AI 改动最可靠的证据。

### 本课范围

本课只练习 Git 和 GitHub 的项目管理方法，不创建业务代码、不修改远程仓库权限、不强推历史、不上传密钥。GitHub 网页的具体按钮会变化；课程只说明目的与验证方式，执行时请以当前 GitHub 官方页面为准。

### 关键决策

课程默认采用“小分支 + 小提交 + 先检查后提交”。不要把“生成整个项目”“修所有报错”“把本机配置也提交”放在同一次改动里。

```text
读取任务与 AGENTS.md
        ↓
git status / git diff
        ↓
创建专用分支 → 完成一个小目标
        ↓
运行检查 → 再看 git diff
        ↓
git add 指定文件 → commit → push/评审
```

### 操作前检查

1. 在课程仓库根目录运行 `git status -sb`，确认当前分支和改动状态。
2. 运行 `git remote -v`；若显示远程地址，确认它是你有权使用的仓库。不要在终端截图或粘贴带令牌的 URL。
3. 阅读 `AGENTS.md`，把允许目录、禁止事项和验证命令写入本次任务笔记。
4. 选择一个只改文档的小任务，例如“补充一条 MVP 不做清单”，不要同时改多个章节。

### 步骤 1

学会在修改前读取 Git 状态和差异。

1. 在终端进入仓库后运行：

```bash
git status -sb
git diff --stat
git diff -- docs/PRODUCT.md
```

2. `git status -sb` 显示分支及已修改/未跟踪文件；`git diff --stat` 显示变化规模；最后一条只显示产品文档的逐行变化。
3. 预期结果：改一个文档时，diff 只出现该文档的预期行；如果突然出现支付配置、证书、本机设置或无关目录，停止，不要提交。
4. 对 Codex 的任何改动重复此检查。AI 的说明不是证据，实际 diff 才是。

### 步骤 2

为一个小任务创建分支并进行最小提交。

1. 从稳定分支更新后，创建语义明确的分支名；例如：

```bash
git switch -c codex/mvp-copy
```

2. 只完成任务笔记中写明的一项改动，运行项目已有检查。
3. 先暂存指定文件，不使用不理解的 `git add .`：

```bash
git add docs/PRODUCT.md
git diff --cached --check
git diff --cached
```

4. 确认暂存内容后创建简短提交：

```bash
git commit -m "docs: clarify MVP boundary"
```

5. 预期结果：`git log -1 --oneline` 能显示刚才的提交；提交只包含该小任务。首次推送分支时，按 GitHub 官方流程确认目标仓库和分支，不上传本机凭据。

### 步骤 3

安全地处理错误改动和 Codex 误改。

1. 仅想丢弃某个尚未暂存文件的改动时，先运行 `git diff -- <文件>`，确认它确实是可丢弃的内容。
2. 确认后使用：

```bash
git restore -- <文件路径>
```

3. 如果文件已暂存但尚未提交，先将它移出暂存区再检查：

```bash
git restore --staged -- <文件路径>
git diff -- <文件路径>
```

4. 已提交或已推送的改动不要急于使用强制命令；记录提交号，先让负责人或 Codex 分析影响，通常用新的修正提交回退。
5. 预期结果：你能撤回一个明确、未提交的错误，而不会删除其他人的工作或重写共享历史。

### 步骤 4

把任务记录和 Codex 协作固定下来。

1. 每项任务在 `docs/OPERATIONS.md` 或自己的任务系统中记录：目标、允许修改目录、禁止内容、验证命令、提交号和遗留风险。
2. 提交前至少运行 `git diff --check` 与项目当前的检查命令；本课程仓库使用：

```bash
node scripts/audit-course.mjs
```

3. 每次让 Codex 工作时，要求它先读 `AGENTS.md`、列出计划、只改指定文件、运行检查、最后报告 diff 摘要。
4. 预期结果：任何稳定版本都能从 Git 历史找到，任何异常改动都能定位到一次小任务而不是一大团文件。

### 常见问题

- **直接在主分支连续修改**：难以回退和评审。为一个目的创建一个短生命周期分支。
- **先 `git add .` 再看 diff**：可能把 `.env`、证书或本机文件加入提交。先看状态，再逐个 `git add`。
- **把 `git reset --hard` 当万能修复**：它会丢弃未提交内容。本课只教确认后的 `git restore -- <文件>`。
- **提交信息写“update”**：无法理解历史。写明类型和目的，例如 `docs: clarify MVP boundary`。
- **让 Codex 自行提交、推送或合并**：先审阅它的改动；对外发布由你明确授权后再进行。

### 安全与合规

不要把密码、验证码、访问令牌、AppID、支付证书、私钥、`.env`、本机路径或真实数据提交到 Git。发现敏感信息已进入提交时，停止继续传播；立即使相应凭据失效或轮换，并按团队流程处理，而不是只删除工作区文件。共享分支不重写历史、不强推，除非负责人明确授权。

### Codex 提示词

```text
角色：你是谨慎的 Git 协作助教。
任务：只审阅本次小任务的 Git 状态、diff 和提交前检查计划；未经明确授权不得修改、暂存、提交、推送或创建分支。
上下文：项目是同城线下到店一对一私教预约平台。课程强调小任务、可审阅 diff、可回退提交；订单、支付、退款和核销由后端处理。
允许范围：只读取 AGENTS.md、README.md、当前任务相关文档和只读 Git 信息；只有我明确指定路径后才可修改该路径。
禁止范围：不得读取或输出凭据、.env、证书、私钥；不得执行 reset --hard、clean、force push、删除分支、提交、推送、合并或修改远程权限。
功能要求：先报告当前分支、改动文件、diff 范围和建议的最小验证；发现超范围文件时停止并说明原因。
安全要求：不显示真实远程令牌、邮箱、路径、AppID、商户号或个人数据；不以隐藏文件名代替内容审查。
测试要求：只运行 git status -sb、git diff、git diff --check 和 node scripts/audit-course.mjs；报告真实输出摘要和未执行原因。
验收要求：我能清楚决定哪些文件该保留、暂存或撤回，且提交前没有格式错误或敏感文件。
报告要求：列出已读文件、发现的改动、建议操作、验证结果、风险和下一步；不要自行提交或推送。
```

### 产出物

1. 分支命名、提交信息和任务记录约定。
2. 一次可审阅的最小文档提交练习。
3. 可复制的 Codex Git 审阅提示词。

### 验收标准

- [ ] 能解释 `status`、`diff`、暂存区、提交和分支的区别。
- [ ] 能在提交前只暂存指定文件并运行 `git diff --cached --check`。
- [ ] 能在确认内容后使用 `git restore -- <文件>` 撤回未提交误改。
- [ ] 未使用 `reset --hard`、强推或未知清理命令。
- [ ] 未将凭据、环境文件或真实数据加入 Git。
- [ ] `node scripts/audit-course.mjs` 通过。

### 自查清单

- [ ] 每个提交只解决一个可描述的任务。
- [ ] 我在暂存前和提交前都看过 diff。
- [ ] 我知道共享历史出现错误时要用修正提交，而不是强制重写。
- [ ] 我让 Codex 先报告，再决定是否允许写入或发布。
