# 第 14 阶段：云函数与后端基础

### 本课目标

建立后端边界：知道哪些操作必须经云函数、每次调用如何校验身份和输入、如何返回统一错误，以及接口文档如何成为三端协作的合同。

### 你将完成

一份云函数职责清单和 `docs/API.md` 接口草案，覆盖登录、教练入驻、排期、预约、支付、退款、核销、收益与后台审核的受控入口；本课不编写完整业务实现。

### 前置条件

- 已完成第 13 课数据模型，理解集合的读写边界与订单不变量。
- 已开通开发环境，能在开发者工具中找到云函数目录或控制台入口。
- 已准备虚构请求示例和错误码，不使用真实用户、订单、支付或生产环境数据。

### 核心概念

云函数是信任边界：客户端只能提出请求，不能决定“谁是谁”“订单能否变更”“价格是多少”“支付是否成功”。云函数从可信登录上下文取得调用方身份，验证输入形状与权限，读取当前数据后判断状态和归属，再通过事务或条件更新写入结果，并只返回调用方应看到的数据。

接口不是页面按钮的同义词。一个安全接口需要明确动作、调用角色、请求字段、响应字段、前置条件、错误码、幂等策略和审计记录。页面应根据稳定错误码给出提示；不要依赖云函数内部错误文本或把敏感原始错误返回给客户端。

### 本课范围

本课只设计统一调用规范与接口草案；不实现支付、退款、订单状态机、消息发送或生产部署。暂不创建空壳云函数来伪装功能完成，后续课程按业务顺序实现并测试每个接口。

### 关键决策

- 使用“按领域划分的云函数/动作”而非页面直连数据库，例如 `auth.login`、`coach.apply`、`schedule.manage`、`booking.create`、`order.transition`。
- 所有写请求都带业务幂等键或由后端生成可追踪请求 ID；外部回调依据外部交易号去重。
- 统一返回 `ok`、`data`、`error.code`、`error.message`；错误码稳定、对用户可理解，内部细节仅进脱敏日志。
- 角色由后端从登录态和 `admins`/`coaches` 状态判定，绝不信任客户端传入的 `role`、金额、订单状态或用户 ID。

### 操作前检查

1. 打开 `docs/DATA_MODEL.md` 与 `docs/ORDER_STATE.md`，标出每个敏感集合的合法写入动作。
2. 列出三端调用者：用户端、私教端、管理后台，以及系统回调；不要把管理员权限混入用户端接口。
3. 约定请求中只传必要 ID 和用户选择值，价格、可用时段、角色、状态转换由后端重新查询和计算。
4. 准备统一错误码前缀，例如 `AUTH_`、`VALIDATION_`、`FORBIDDEN_`、`CONFLICT_`、`NOT_FOUND_`、`SYSTEM_`。

### 步骤 1

把操作分为“可直接读取”和“必须后端写入”。公开的已上架教练、项目、场馆列表可以受最小权限规则读取；登录资料初始化、教练入驻、排期变更、创建预约、支付发起与确认、取消退款、核销、评价发布、收益结算、提现和后台审核全部必须走云函数。

为每个动作写出调用方和授权条件。例如 `booking.create` 只能由已登录用户为自己创建；`schedule.manage` 只能修改当前审核通过教练自己的未来时段；`admin.reviewCoach` 必须由有效管理员角色调用；支付回调不能接受客户端模拟结果。将这份责任表写入 `docs/API.md`，而不是只散落在页面注释中。

### 步骤 2

为写接口设计固定处理顺序：①读取可信身份；②校验请求字段类型、长度、枚举和必填项；③查询当前对象并校验归属、状态、时间窗口；④在事务或条件更新中写入；⑤追加审计日志；⑥返回最小响应。失败时不要部分写入，也不要把数据库堆栈、凭据或其他用户数据返回。

例如预约创建请求只可传 `coach_id`、`project_id`、`venue_id`、`schedule_id` 与幂等键；后端自行核对教练已上架、项目与场馆关联有效、时段可约、价格快照与用户身份。若时段已被占用，返回 `CONFLICT_SLOT_UNAVAILABLE`，页面刷新可约时段，而不是自行修改订单状态。

### 步骤 3

定义统一错误与可观察性。客户端可见的错误码应包括：`AUTH_REQUIRED`、`FORBIDDEN`、`VALIDATION_FAILED`、`NOT_FOUND`、`CONFLICT_SLOT_UNAVAILABLE`、`STATE_TRANSITION_INVALID`、`PAYMENT_PENDING`、`SYSTEM_RETRYABLE`。每个错误对应安全、简短的用户提示；内部日志记录请求 ID、函数名、结果和必要的脱敏上下文。

日志不得写入手机号、证件、完整支付标识、令牌、密钥或未经脱敏的请求体。处理外部回调时还要记录验证结果、幂等命中与关联订单 ID，但回调验签细节和密钥只保留在受控环境配置中。平台运行时、日志与鉴权接口可能更新，执行时请以微信公众平台当前页面和官方文档为准。

### 步骤 4

用两条虚构请求走读接口草案：一条成功的 `booking.create` 请求和一条被占用时段请求。前者的预期结果是返回订单 ID、待支付状态和整数分金额；后者的预期结果是稳定冲突错误码且不创建第二个有效订单。此处只验证接口文档的输入、授权、输出和失败语义，不调用真实支付。

审阅每一项是否有后端唯一责任：谁验证身份、谁确定金额、谁写订单、谁执行退款、谁保存审计。如果答案是“页面自己处理”，说明边界仍有漏洞，应把动作收回云函数设计。把尚未实现的动作标为计划，不对外宣称已上线。

### 常见问题

- **客户端传了 `user_id` 就直接使用：** 应以登录上下文为准，客户端 ID 只能作为被校验的业务参数。
- **把 `role: admin` 作为鉴权依据：** 客户端字段可伪造；必须查询受控管理员角色和状态。
- **失败后返回原始异常：** 原始异常可能泄露集合、字段或凭据。记录脱敏日志，客户端只收稳定错误码。
- **创建订单后再检查时段：** 检查和占用必须处于同一后端受控事务/条件更新范围，避免竞态。
- **将支付成功当作页面回调：** 支付结果必须以后端可信回调或主动查单为准，页面仅展示处理中或已确认状态。

### 安全与合规

云函数配置、商户证书、API 密钥、回调密钥和生产环境标识只通过受控环境变量或平台密钥管理注入，不进入仓库、课程正文、日志、截图或提示词。接口响应遵循最小披露，不把其他用户资料、后台审核意见或支付原文返回给无权角色。

订单、支付、退款、核销、余额、收益、流水与提现状态均由后端校验并写入；金额使用整数分；所有敏感动作应有请求追踪和审计记录。执行时请以微信公众平台当前页面和官方文档为准。

### Codex 提示词

```text
角色：你是资深微信小程序、微信云开发与后端安全工程师，严格遵守项目根目录 AGENTS.md。

任务：为 YourCoach 完善 docs/API.md，定义云函数职责、统一请求响应、错误码、鉴权、幂等和审计要求；不实现完整业务代码。

上下文：平台包含用户端、私教端、PC 管理后台和云开发后端。数据模型已定义 19 个集合；订单、支付、退款、核销、收益和提现是敏感状态，客户端不可信。

允许范围：仅修改 docs/API.md、docs/SECURITY.md、docs/ORDER_STATE.md 及本课明确需要的文档；可使用完全虚构的请求响应示例。

禁止范围：不得接入真实支付、调用生产接口、写入密钥或证书、创建伪实现云函数；不得修改无关 UI、架构或依赖；不得输出个人信息或生产配置。

功能要求：覆盖登录、入驻、排期、预约、订单状态、支付、退款、核销、评价、收益、提现和后台审核；统一定义 ok/data/error、稳定错误码、后端确定价格与状态、请求幂等和审计日志。

安全要求：从可信登录上下文鉴权；校验类型、归属、状态、时间和金额；不信任客户端角色、用户 ID、价格或支付结果；敏感写入只由后端执行；日志与示例必须脱敏。

测试要求：为至少一条成功预约和一条时段冲突请求写出最小验证步骤、预期响应和无副作用断言；不得依赖真实用户、支付、凭据或生产环境。

验收要求：每个敏感动作都有后端责任、授权条件、错误处理与审计要求；接口文档可供三端调用；无秘密信息、无未说明的假接口。

报告要求：列出修改文件、接口决策、验证案例、未实现项、风险与下一步；附 git diff 摘要，不要自行提交。
```
