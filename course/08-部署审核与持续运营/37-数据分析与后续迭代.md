# 第 37 阶段：数据分析与后续迭代

### 本课目标

建立基于目标和证据的持续运营循环：只收集必要的聚合事件与反馈，定义可解释指标，发现问题后形成最小假设、有限实验、验收标准和回滚路径，而不是凭直觉扩展功能。

### 你将完成

指标字典、数据质量检查、反馈/问题台账、迭代优先级框架和下一轮实验模板。

### 前置条件

- 已有稳定版本、发布观察、错误/订单/运营记录和隐私安全基线。
- 已确认当前阶段只做同城到店一对一 MVP，不以数据为由扩大个人信息收集或未验证功能。
- 数据/运营负责人明确，能查看受控聚合指标和脱敏问题记录。

### 核心概念

指标要回答业务问题而不是制造数据：用户能否找到可约教练？是否成功完成预约？支付/退款是否可靠？服务是否完成？供给是否足够？系统是否安全稳定？每个指标都要有事件定义、计算口径、时间范围、负责人、数据源、隐私边界和行动阈值。

迭代以“问题—证据—假设—最小改动—验收—观察/回滚”闭环。相关性不等于因果；漏斗下降可能来自供给、价格、时段、网络、授权、页面、支付或数据质量，先分段验证，不用一次大改动同时改变多个变量。

### 本课范围

本课只设计 MVP 所需的聚合运营指标和改进流程，不建设用户画像、跨站追踪、广告归因、复杂数据仓库、个性化推荐或大规模实验平台。任何新增数据字段/第三方分析 SDK 都需重新走隐私、安全和审核评估。

### 关键决策

- 事件按最小必要原则记录：匿名/脱敏会话或请求摘要、事件名、时间、版本、状态/错误分类；不记录不必要的精确位置、完整身份、支付凭据或页面输入。
- 核心漏斗：有效浏览 → 选择教练/场馆/时段 → 创建订单 → 可信支付确认 → 确认/核销 → 完课 → 评价；按城市、版本、项目/场馆等非敏感维度聚合。
- 可靠性指标：订单状态滞留、支付/退款未决、排期冲突、云函数错误、权限拒绝、通知失败、客服问题；设置阈值和负责人。
- 优先级同时考虑影响、证据强度、风险、工作量、合规/安全和可逆性；资金、权限、数据质量问题优先于体验优化。

### 操作前检查

1. 从 `docs/OPERATIONS.md`、`docs/TEST_PLAN.md`、订单/支付/退款日志提取已有可用、脱敏数据源。
2. 为每个核心指标写清事件、分子/分母、时间窗口、过滤条件、负责人和误用风险。
3. 检查事件/日志字段未包含真实个人资料、支付原文、密钥、证件、精确位置或可复用令牌。
4. 建立问题台账，区分用户反馈、客服工单、监控告警、测试缺陷与数据质量问题。

### 步骤 1

定义最小指标字典。产品健康：已上线教练/有效场馆/可约时段数量；预约漏斗：浏览、选择、创建、支付确认、完课；履约质量：取消、退款、超时、核销/完课滞留；稳定性：错误、延迟、崩溃、权限拒绝；支持：问题类型、首次响应、解决状态。每项只看聚合趋势和必要分段。

为金额指标明确口径：使用可信支付/退款/订单快照的整数分聚合，模拟支付和测试数据必须排除。不要把“创建订单数”误当作“收入”，也不要把未决支付或退款中金额计入完成交易。

### 步骤 2

建立数据质量检查：事件是否因版本/网络丢失？状态时间线是否能闭合？支付/退款与订单是否一致？是否混入测试/模拟记录？指标突变是否来自口径变更？每次发布同步记录事件版本和数据字典变更，避免把埋点变更误判为业务增长/下降。

当发现异常，先以订单/状态机/日志为权威事实回查，而不是直接修改报表。数据修正采用可追溯补算或标注，不静默覆盖原始审计事件。

### 步骤 3

把反馈和指标转为问题陈述：例如“某城市用户看到可约时段后未创建订单的比例上升，且无支付错误增多”。收集可验证证据，提出单一假设，如“场馆选择步骤在弱网下加载失败”，设计最小修复/实验、成功阈值、风险、受影响范围、回滚和测试。

优先处理安全、资金、权限、数据完整性和高频阻断问题；再处理供给/履约和体验问题。涉及新权限、新数据、支付、定位、自动化决策或营销的迭代必须重新评审隐私、合规和审核影响。

### 步骤 4

运行固定运营节奏：日常查看关键告警和未决订单；每周复盘漏斗、履约、退款、供给和支持；每次版本发布后对比基线；每个迭代完成后用预定义指标验证并记录是否保留、回滚或继续观察。会议结论必须落到负责人、范围、验收和截止时间。

输出下一轮优先级表：问题、证据、假设、最小范围、风险、指标、验收、负责人、依赖和回滚。未有足够证据的想法进入观察池，不直接进入开发。执行时请以微信公众平台当前页面和官方文档为准。

### 常见问题

- **收集越多数据越好：** 过度数据增加风险和噪声，先满足明确问题。
- **只看总量：** 需按版本、城市、状态等非敏感维度定位变化。
- **将测试/模拟支付计入收入：** 必须标识并排除。
- **指标下降就立刻大改 UI：** 先检查数据质量、供给、错误和单一假设。
- **迭代没有验收：** 无法判断有效，必须预先定义成功/失败和回滚。

### 安全与合规

运营分析遵循最小必要、聚合优先、用途明确、受控访问、最短保留和脱敏原则。不得使用指标系统收集真实敏感资料、精确轨迹、支付原文、凭据或生产配置；新增数据/SDK/权限需重新评审。订单、支付、退款、钱包事实仍以后端审计数据为准。执行时请以微信公众平台当前页面和官方文档为准。

```text
角色：你是资深产品数据、交易运营与隐私工程师，严格遵守项目根目录 AGENTS.md。

任务：建立 YourCoach MVP 的最小指标字典、数据质量检查、问题台账与证据驱动迭代模板；不扩大数据收集。

上下文：平台有订单、支付、退款、履约、供给、通知和发布监控。MVP 为同城到店一对一服务，隐私和安全基线已建立。

允许范围：仅修改课程、docs/OPERATIONS.md、docs/PRODUCT.md、docs/TEST_PLAN.md 和脱敏运营模板/查询；复用现有日志与状态数据。

禁止范围：不得接入未经审查的分析 SDK、收集精确位置/个人资料/支付原文、混入测试数据、做未经验证大改动或修改无关代码。

功能要求：定义漏斗、履约、供给、稳定性、支持和账务口径；事件最小化；数据质量检查；问题—假设—最小实验—验收—回滚—复盘流程。

安全要求：聚合/脱敏、最小访问、测试/模拟隔离、可信状态机为事实来源；新增字段/权限走隐私与合规评审。

测试要求：用虚构聚合数据验证指标公式、测试数据排除、状态一致性、问题优先级和实验验收；说明预期结果。

验收要求：每个迭代可追溯到目标、证据、范围、风险、指标和验收；无敏感数据泄露或无依据扩张。

```

### 产出物

### 验收标准

- [ ] 每个核心指标有目的、口径、数据源、时间范围、负责人、隐私边界和行动阈值。
- [ ] 测试/模拟数据、未决支付/退款与真实聚合口径明确隔离。
- [ ] 数据质量、状态一致性和口径变更均可检查和追溯。
- [ ] 迭代项均有证据、假设、最小范围、风险、验收和回滚。
- [ ] 未收集或暴露真实敏感资料、凭据、交易或生产配置。

### 自查清单

- [ ] 未用总量掩盖供给、错误或履约问题。
- [ ] 未因指标需求新增未评审的数据字段/权限。
- [ ] 已排除模拟支付、测试订单和重复事件。
- [ ] 高风险问题优先于体验/营销优化。
- [ ] 每次迭代有明确保留/回滚/继续观察决策。
