# 第 15 阶段：微信登录与用户系统

### 本课目标

设计一个以可信登录态为中心的最小用户系统：用户无需手工填写平台身份标识，后端负责识别身份、创建最小档案、限制资料修改范围，并为用户、教练和管理员角色提供统一入口。

### 你将完成

- 登录交互与后端流程说明。
- `users` 集合的最小字段、更新规则和注销/资料边界。
- `auth.login`、`user.updateProfile` 的接口验收案例。

### 前置条件

- 已完成第 13 课的数据模型和第 14 课的云函数接口契约。
- 已能在开发环境使用测试账号验证小程序登录态。
- 已确认本课不要求索取手机号、身份证、银行卡或任何非业务必需资料。

### 核心概念

登录证明“当前请求来自哪个微信用户”，资料授权证明“用户同意提供哪些可选展示资料”，两者不能混为一谈。云函数应从可信上下文取得用户身份，为首次登录创建最小 `users` 文档，为再次登录返回同一用户；前端不得把自行传入的身份标识当作可信依据。

用户角色是业务权限，不是客户端开关。一个账号可以先是普通用户，之后提交教练申请；教练资格由 `coaches.audit_status` 决定，后台权限由 `admins` 受控决定。页面可以据此调整入口，但每次敏感动作仍要由后端重新鉴权。

### 本课范围

本课设计登录和最小资料维护，不实施手机号能力、实名认证、营销画像、社交关系或多端单点登录。若未来确有收集需求，必须在独立需求评审中说明目的、最小字段、保存期限、授权与删除机制。

### 关键决策

- 首次登录只创建业务必需的用户记录：内部关联、状态、创建/更新时间；昵称和头像均为可选展示资料。
- `users` 不公开手机号、身份标识、设备信息或完整授权原文；展示字段有长度、内容和来源限制。
- 资料更新采用字段白名单，后端忽略或拒绝角色、余额、审核状态等客户端传入字段。
- 账号停用、注销和资料导出请求通过受控流程处理，不由页面直接删除数据库文档。

### 操作前检查

1. 对照 `docs/DATA_MODEL.md` 确认 `users`、`coaches`、`admins` 的职责分离。
2. 列出页面需要的最小用户信息：登录状态、展示名称、头像占位、教练/管理员入口摘要。
3. 准备两个虚构测试账号场景：首次登录与重复登录；不记录真实身份标识或截图。
4. 在开发环境检查云函数调用权限和日志脱敏策略。

### 步骤 1

画出登录时序：用户打开页面 → 页面请求登录能力 → 调用 `auth.login` → 云函数取得可信上下文 → 查找或创建 `users` → 返回最小用户摘要与可用角色。页面只根据 `ok/data/error` 更新状态；网络失败显示可重试提示，不把“未能登录”误当作新用户。

首次登录的预期结果是一个状态正常、无多余资料的用户文档；重复登录的预期结果是同一用户文档被读取或仅更新时间更新，绝不产生重复用户。把“查找+创建”放在后端受控逻辑中，并为重试设置幂等行为。

### 步骤 2

定义 `users` 字段白名单：系统维护 `status`、`created_at`、`updated_at`；用户可申请更新 `nickname`、`avatar_url` 等展示字段；角色、审核状态、内部身份关联、余额、订单归属永远不接受客户端直接写入。对于昵称、简介等文本，校验类型、长度、空值和不安全内容；不要把整段页面状态对象直接写入数据库。

为资料授权设计“可拒绝、可跳过、可后续修改”的交互。拒绝提供头像或昵称不应阻断浏览和预约；只有确实需要联系或履约的环节再告知目的和范围。任何平台授权入口、返回字段或审核规则变化，执行时请以微信公众平台当前页面和官方文档为准。

### 步骤 3

为注销与资料请求预留流程。用户发起请求后，后端先核验身份和未完成订单、退款、提现等保留义务，再按政策执行匿名化、限制处理或延后删除；不能直接删除会破坏交易审计的订单与资金流水。资料导出也只提供用户有权获得的最小数据，不含其他用户、后台审核或支付内部信息。

记录待业务与法务确认的问题：需要收集哪些资料、每项目的是什么、保存多久、用户如何撤回、如何响应删除/导出请求。课程中只记录流程，不给出变化性法规结论。

### 步骤 4

使用虚构测试账号做两项走读。首次调用 `auth.login`：预期创建最小档案并返回用户摘要；再次调用：预期返回同一业务用户而非新增记录。随后尝试通过 `user.updateProfile` 提交允许的展示字段：预期成功；提交 `role`、`status` 或 `balance_cent`：预期被忽略或返回 `FORBIDDEN/VALIDATION_FAILED`，且数据库敏感字段不变。

检查日志只含请求 ID、动作和结果，不含完整身份标识、头像原始地址、授权原文或个人资料。验证无法在开发环境完成时，记录原因和手工验收步骤，不把未验证写成已上线。

### 常见问题

- **每次登录都新建用户：** 后端应以可信身份关联做查询与幂等创建；不要用昵称或头像判断同一人。
- **把昵称和头像设为登录必填：** 它们是可选展示资料，用户拒绝时仍应可使用基础服务。
- **前端传 `role` 后就显示管理员功能：** UI 可隐藏入口，但权限必须由后端查询 `admins` 和状态决定。
- **直接删除 `users` 处理注销：** 会破坏订单、退款和审计关联；应走审核后的匿名化/保留流程。
- **日志打印整个登录响应：** 容易扩大个人数据暴露面，只保留最小脱敏诊断字段。

### 安全与合规

坚持最小化收集、明确用途、可拒绝和受控保留。不得在课程、代码、日志、截图或仓库中写入真实 AppID、身份标识、手机号、头像原始数据、授权票据、密钥或生产配置。敏感资料不因“开发方便”而公开读取。

客户端不可信：后端必须从可信登录上下文识别用户，并校验字段白名单、归属和角色。账号注销、导出、删除、授权能力和隐私规则均须以实际产品流程和当前官方要求为准。执行时请以微信公众平台当前页面和官方文档为准。

测试要求：使用虚构测试账号验证首次登录、重复登录、允许字段更新和敏感字段拒绝四种情况；说明操作、预期结果与失败定位；不得依赖真实用户或生产凭据。

验收要求：无重复用户、无客户端伪造角色入口、无敏感字段直写；资料收集目的和后续注销边界明确；无秘密信息或未说明的假接口。

报告要求：列出修改文件、身份与字段决策、验证结果、未执行项及原因、隐私风险和下一步；附 git diff 摘要，不要自行提交。

### 验收标准

- [ ] 首次和重复登录均能映射到唯一业务用户。
- [ ] 昵称、头像等可选资料不阻断基础使用。
- [ ] 客户端不能直接写角色、状态、余额或内部身份关联。
- [ ] 用户、教练、管理员角色由后端受控状态判断。
- [ ] 已记录注销/导出与未完成交易的处理边界。
- [ ] 未出现真实身份信息、凭据或生产数据。

### 自查清单

- [ ] 每个收集字段都有明确用途，且不存在“以后可能有用”的字段。
- [ ] 前端不保存或打印不必要的授权结果。
- [ ] 登录失败和网络失败有可重试提示，不创建错误用户。
- [ ] 已检查开发环境日志与 git diff 的脱敏情况。
- [ ] 已标记需人工核实的官方规则。
