# 第 18 阶段：教练排期系统

### 本课目标

设计可约时段、停用和占用规则，使教练能维护未来服务时间，而用户只能看到并尝试预约有效时段；并发冲突最终由后端保证。

### 你将完成

- `coach_schedules` 的字段、状态和时段粒度约定。
- 教练创建/停用时段、用户查看、订单锁定时段的后端规则。
- 时段冲突、请假和临近服务变更的最小验收案例。

### 前置条件

- 已完成项目、场馆与有效教练关联设计。
- 已理解订单必须选择教练、项目、场馆和时段。
- 已阅读 `docs/DATA_MODEL.md`、`docs/API.md` 的排期和预约接口约定。

### 核心概念

排期是“可供预约的候选资源”，不是订单本身。时段包含教练、场馆、开始时间、结束时间和状态；用户看到 `AVAILABLE` 时段也不等于已经占有它，真正的占用必须与订单创建在后端事务或条件更新中完成。

状态至少区分 `AVAILABLE`、`HELD`、`BOOKED`、`UNAVAILABLE`、`CANCELLED`。`HELD` 用于短暂支付窗口，超时应由后端收回；`BOOKED` 对应有效已支付或待履约订单；临近服务时段不能被教练无痕删除，以免用户预约失联。

### 本课范围

本课只做固定时段排期和单教练资源冲突，不做循环排班、跨时区、多人团课、候补、智能推荐或日历同步。时区统一按产品服务城市处理，具体存储和展示实现于后续工程课程验证。

### 关键决策

- 所有时段以明确开始/结束时间保存，使用统一服务时区和时间戳，不依赖客户端本地格式。
- 教练只可维护自己的未来时段，且场馆必须是有效 `coach_venues` 关联。
- 时段状态和订单状态分开：订单成功后由后端改变时段；前端不直接把时段改为已约。
- 同一教练相交时段不允许同时 `AVAILABLE/HELD/BOOKED`，冲突检测在后端执行。

### 操作前检查

1. 确认时段粒度（例如 30 分钟）和最小服务时长已由产品确认；未确认时记录为待决项。
2. 准备一个虚构教练、有效场馆关联及三个未来时段。
3. 列出需要拦截的情况：过去时间、结束早于开始、无效场馆、相交时段、已被预订时段、临近服务取消。
4. 确认订单状态机将负责超时释放和支付成功占用，教练端不承担资金状态判断。

### 步骤 1

定义 `coach_schedules` 最小字段：`coach_id`、`venue_id`、`start_at`、`end_at`、`status`、`hold_expires_at`（仅锁定时使用）、创建和更新时间。新建时段前，云函数校验调用人就是该教练、时间在允许窗口内、场馆关联有效、结束晚于开始且没有与有效时段相交。

查询用户可约时段时，同时过滤教练上线、场馆/关联有效、`status=AVAILABLE` 和未来时间；不要仅凭前端本地时间显示。预期结果是用户看不到草稿、已取消、锁定、已约或失效场馆的时段。

### 步骤 2

约定时段变更。教练可编辑或取消尚未锁定且未被预订的未来时段；对 `HELD`、`BOOKED` 或临近开始的时段，云函数返回稳定错误或引导走取消订单/人工处理流程。请假不通过删除历史记录实现，而是将未约未来时段置为不可约，并保留必要原因分类与审计。

场馆关联下架或教练下架时，停止该组合的新排期和新预约；已生效订单依照订单状态机通知、履约、取消或退款。不要用批量前端写入把所有时段改成同一状态。

### 步骤 3

设计预约锁定：`booking.create` 在同一受控操作中验证时段仍为 `AVAILABLE`，创建待支付订单并写入 `HELD`、锁定过期时间；支付确认前如过期，后端关闭订单并恢复 `AVAILABLE`；可信支付成功后将时段置为 `BOOKED`。重复调用使用幂等键，绝不能创建两个有效订单。

数据库唯一索引只能解决部分重复写入，不能取代条件更新和状态校验。并发测试应以“两个请求争抢同一时段”为例：一个成功，另一个得到 `CONFLICT_SLOT_UNAVAILABLE`，无重复扣款、无多余订单、无错误恢复。

### 步骤 4

用虚构数据走读四项：创建一个有效未来时段成功；创建相交时段被拒绝；用户尝试预约时段后变为 `HELD`；第二次预约相同时段被拒绝。再模拟锁定超时，预期订单不进入已支付状态，时段仅在后端确认未关联有效订单后恢复可约。

记录不在本课验证的内容，例如定时任务调度、真实支付回调或跨端日历展示。验证失败时先检查可信身份、场馆关联、时间比较和条件更新，而不是放宽权限。

### 常见问题

- **用页面按钮防止重复预约：** 多个设备仍会并发，必须后端条件占用。
- **把时段删除当作请假：** 会丢失审计和订单关联，使用状态变更与受控原因。
- **只检查开始时间相等：** 相交区间也会冲突，应判断 `newStart < oldEnd && oldStart < newEnd`。
- **支付超时后只关闭订单：** 必须同时安全释放对应 `HELD` 时段，且不能释放已支付订单。
- **根据客户端时区判定过去时间：** 使用统一服务端时间和产品时区约定。

### 安全与合规

排期写入、锁定、释放和订单关联均由后端完成；客户端只能提交候选时段，不能传入最终状态或锁定结果。时间、场馆、教练归属与订单状态均需后端重查。日志不得包含真实行程、精确住址、身份信息、凭据或生产数据。

服务时间、通知、取消窗口和平台能力可能变化，执行时请以微信公众平台当前页面和官方文档为准。

### 验收标准

- [ ] 教练只能维护自己的有效场馆关联下的未来时段。
- [ ] 相交有效时段被后端拒绝，用户只读取可约时段。
- [ ] 预约创建、锁定、支付确认和超时释放有一致状态规则。
- [ ] 同一时段并发请求最多产生一个有效订单。
- [ ] 已明确临近服务和已约时段不可直接删除。
- [ ] 未使用真实行程、个人信息、凭据或生产配置。

### 自查清单

- [ ] 时间比较由服务端统一时间/时区约定执行。
- [ ] 锁定、订单和支付没有由页面分别独立修改。
- [ ] 已覆盖相交区间而非只覆盖相同开始时间。
- [ ] 超时释放不会影响已支付或履约订单。
- [ ] 已检查测试数据、日志与 git diff 的脱敏。
