# 第 17 阶段：场馆与运动项目管理

### 本课目标

定义项目、场馆与教练服务关系的单一事实来源，确保用户只能预约已上架项目、有效场馆和已审核关联，不因后台资料变更而改写历史订单。

### 你将完成

- `projects`、`venues`、`coach_venues` 的维护与展示边界。
- 用户选场馆、教练配置服务点、后台审核关联的规则。
- 项目/场馆下架时对排期、在途订单和用户页面的处理原则。

### 前置条件

- 已完成教练入驻审核，理解“审核通过”与“公开上线”不同。
- 已完成数据模型和云函数接口约定。
- 已确认 MVP：每个教练一个主项目，可关联多个场馆；下单时必须选择场馆。

### 核心概念

`projects` 是平台维护的标准服务项目，`venues` 是可服务的实体场馆，`coach_venues` 是教练与场馆之间的有效关联。三者不能互相替代：项目定义服务内容与基础时长/价格，场馆定义服务地点，关联记录定义某教练是否能在该地点提供该项目及是否存在受控价格覆盖。

订单必须保存项目、场馆、教练和价格的交易快照。项目改名、场馆地址调整或教练取消合作后，历史订单仍应显示当时确认的服务信息；新订单则必须重新校验对象及关联是否有效。

### 本课范围

本课设计后台维护、公开展示和下架策略，不接地图导航、不计算距离、不创建复杂套餐、多项目、团课或动态定价。场馆合作协议、资质、地址真实性与费用规则由业务流程另行确认。

### 关键决策

- `projects.status`、`venues.status` 和 `coach_venues.status` 均须有效，用户端才展示并允许预约。
- 教练只能申请或维护自己关联的场馆意向；新增、审核、下架和高风险资料变更由管理员云函数处理。
- 主项目以 `coaches.main_project_id` 表示；MVP 不允许同一教练同时公开多个主项目。
- 价格基础值来自项目，若允许场馆/教练差异价，使用整数分的 `price_override_cent`，由后端明确优先级并写入订单快照。

### 操作前检查

1. 阅读 `docs/DATA_MODEL.md` 中三集合字段和订单快照约定。
2. 准备虚构的项目、两个场馆、一个已审核教练及两条关联记录。
3. 列出用户端实际查询：项目详情、教练可服务场馆、指定场馆下可预约教练。
4. 与运营确认哪些资料是公开展示字段，哪些仅后台或合作方可见。

### 步骤 1

为项目定义最小字段：名称、服务说明、时长分钟数、基础价格分、状态和更新时间。只有 `ACTIVE` 项目可出现在新订单；项目修改需要后台受控操作，且不能用新价格覆盖已有订单。用户端展示文案应来自已审核的公开字段，不展示内部成本、审核备注或配置键。

为场馆定义名称、地址文本、位置摘要、状态和必要的展示设施信息。地址的精确程度需按隐私和业务需要决定；不要在课程样例中填真实地址。场馆下架时应停止新排期/新预约，但不能删除已有订单所需的快照。

### 步骤 2

用 `coach_venues` 表达多对多关系，字段至少包括 `coach_id`、`venue_id`、`status`、`price_override_cent`（可选）、创建和更新时间。对同一教练和场馆建立唯一约束，避免重复关联。教练端提交关联意向，后台审核生效；用户端只查询教练已上线、场馆已上线、关联有效的组合。

创建预约时，后端同时验证：教练主项目存在且上架、所选场馆上架、教练-场馆关联有效、该时段属于该教练且可约。客户端传入的项目、场馆、价格只作为候选参数，不能绕过交叉校验。

### 步骤 3

定义变更策略。项目/场馆/关联下架后：停止创建新时段或新订单；已创建但未支付的订单按状态机取消或提示重新选择；已支付、待服务和已完成订单依据订单快照履约、取消或退款规则处理。不要通过直接删除集合文档让历史订单失去关联。

价格变更采用“对新订单生效”。后端在创建订单时读出当前有效价格，确定 `amount_cent` 后写入快照；支付、退款、收益均以订单快照金额为准。任何例外优惠也要有明确后端来源和审计，不允许页面自行计算最终金额。

### 步骤 4

使用虚构数据验证三种查询：已上架项目列表、某已上架教练的有效场馆列表、指定场馆下的可预约教练。预期结果不含下架项目、下架场馆或失效关联。然后尝试使用失效关联创建预约，预期返回 `VALIDATION_FAILED` 或稳定的不可预约错误，且不产生订单。

记录一项下架演练：将虚构关联置为非有效状态后，确认新预约被拒绝、历史订单展示使用快照。此验证只在开发环境进行，不删除记录或改动生产数据。

### 常见问题

- **在 `coaches` 里存场馆数组：** 多对多关系难以审核、索引和下架，使用 `coach_venues` 作为独立关联记录。
- **项目价格变动后更新全部订单：** 历史交易必须使用下单快照，更新会破坏对账和退款。
- **前端只根据页面隐藏判断下架：** 后端创建订单仍要交叉校验三种状态。
- **删除下架场馆：** 会破坏历史订单，使用状态控制新业务而不是物理删除。
- **把精确地址和合作备注全部公开：** 展示字段与内部合作资料必须分层。

### 安全与合规

项目、场馆和关联的上架/下架由后端授权控制；订单创建重新查询有效状态和价格，金额以整数分保存。不得在示例、日志、截图或仓库写入真实地址、合同、联系方式、身份信息、凭据或生产配置。

地图展示、地址精度、场馆资质、广告宣传和隐私告知均应以实际业务和当前平台规则为准。执行时请以微信公众平台当前页面和官方文档为准。

### 验收标准

- [ ] 教练主项目、场馆和有效关联均是新预约的必要条件。
- [ ] 同一教练-场馆组合不重复，只有有效组合向用户端展示。
- [ ] 金额为整数分，价格/名称/场馆信息在订单中保留快照。
- [ ] 下架停止新业务，不删除历史订单关联。
- [ ] 公开字段与内部资料分离，未使用真实数据或凭据。

### 自查清单

- [ ] 已用虚构数据验证查询和拒绝路径。
- [ ] 已检查 git diff 与日志脱敏。
