# 第 32 阶段：双端联调与完整流程测试

### 本课目标

在同一隔离开发环境中，用同一组虚构角色和订单验证用户端、私教端、后台和云函数是否对同一业务事实达成一致，并把主流程和异常流程留下可复现证据。

### 你将完成

联调数据包、主流程剧本、异常矩阵、跨端状态核对表和缺陷记录格式。

### 前置条件

- 三端开发版本、云函数、模拟支付和自动化核心检查可运行。
- 测试计划已定义订单、排期、支付、退款、核销和权限不变量。
- 已准备独立开发环境与完全虚构用户、教练、管理员、项目、场馆和时段。

### 核心概念

联调验证的是“同一事实的传播”：用户端创建订单后，私教端和后台应按授权看到同一订单摘要；模拟支付、确认、核销、完课、退款后，订单、排期、支付、退款、钱包/通知日志应一致。不同端的页面文案可以不同，但不能各自维护不同状态。

联调不等于只跑一条成功路径。每个关键动作都要验证授权、错误码、重复请求、网络恢复、并发冲突和无副作用；错误必须回到共享接口/状态机根因，而非在某一个页面临时隐藏。

### 本课范围

本课只在开发/测试环境用模拟支付和脱敏数据联调，不执行真实支付、真实提现、生产审核、真实模板发送或生产数据导入。真机/体验版特有能力在下一课验证。

### 关键决策

- 一次联调固定数据包和环境别名，结束后清理/隔离；不混用个人测试数据。
- 主流程以订单 ID、请求 ID、时段 ID、状态版本为关联证据，避免靠截图猜测。
- 每个动作同时记录发起端、后端响应、其他端可见结果、集合/日志摘要和是否有副作用。
- 缺陷分为阻断（资金/权限/状态）、高（主路径）、中（体验/提示）、低（文案），阻断/高未关闭不得进入体验版。

### 操作前检查

1. 固定虚构角色：用户 U、教练 C、管理员 A；项目 P、场馆 V、时段 S、金额 `9900` 分。
2. 清空或隔离旧测试订单，确认没有生产配置、真实支付或真实用户。
3. 从 `docs/ORDER_STATE.md` 列出主状态和异常状态的预期。
4. 准备请求/日志查看权限，仅记录脱敏 ID 和状态，不复制隐私/凭据。

### 步骤 1

执行主流程：用户端浏览已上线教练→选择有效场馆/时段→创建 `PENDING_PAYMENT` 订单；私教端看到待确认摘要；模拟支付后时段由 `HELD` 变 `BOOKED`；教练确认→核销→完课；用户端创建评价；后台查看受控审计摘要。每个节点核对订单状态、排期状态和日志。

预期：用户只见自己的订单，教练只见本人订单，后台只按角色看必要数据；页面刷新后仍以服务端状态为准；评价只在完课后可用。

### 步骤 2

执行取消/退款流程：创建另一笔虚构订单，支付确认后按政策发起退款；检查 `REFUNDING`、可信确认后的 `REFUNDED`、时段联动、支付/退款记录和收益冻结/冲回。用后台发起受控异常动作，不通过直接改数据库模拟。

同时验证支付超时：创建待支付订单后触发/模拟超时，预期订单关闭、符合条件时段释放、再次预约可用，且没有支付/钱包副作用。

### 步骤 3

执行异常矩阵：两用户抢同一时段；同一支付/退款回调重复；用户读取他人订单；教练修改他人排期；普通用户访问后台；前端篡改金额/状态；网络超时后重复点击；通知失败。每项预期稳定错误、最小安全提示和无重复写入。

发现不一致时记录跨端时间线和请求 ID，先检查共享后端状态/鉴权/幂等，而不是各端分别修补。

### 步骤 4

输出联调报告：环境别名、数据代号、剧本、操作人角色、请求/响应摘要、状态证据、缺陷等级、根因、修复提交和回归结果。将未覆盖第三方能力、真机权限和生产流程显式列出。

联调退出条件是主流程、退款/超时、并发/权限异常均有证据；阻断和高缺陷关闭或经负责人签字接受。执行时请以微信公众平台当前页面和官方文档为准。

### 常见问题

- **三端使用不同测试订单：** 无法验证一致性，应使用同一订单 ID 贯穿。
- **只截图不查后端状态：** UI 可能缓存，必须核对状态和日志。
- **用管理员权限测试用户流程：** 会掩盖权限问题，角色必须隔离。
- **异常后手工改数据库恢复：** 会绕过问题，应以新虚构数据或受控清理重跑。
- **网络超时就判失败：** 先刷新订单/查幂等结果，避免重复创建。

### 安全与合规

联调仅使用隔离环境和虚构数据，日志、截图和缺陷单脱敏；不复制真实订单、支付、位置、证书或凭据。关键状态均经后端，测试人员不得用控制台越权修改业务事实。执行时请以微信公众平台当前页面和官方文档为准。

### Codex 提示词

```text
角色：你是资深端到端测试、交易状态机与跨端联调工程师，严格遵守项目根目录 AGENTS.md。

任务：组织用户端、私教端、后台和云函数的隔离联调，输出主流程、异常流程、一致性证据和缺陷结论。

上下文：YourCoach 使用订单状态机、模拟支付、排期锁定和角色授权；禁止使用生产数据和真实资金。

允许范围：仅修改测试/联调记录、必要测试代码、课程和 docs/TEST_PLAN.md；使用虚构脱敏数据。

禁止范围：不得调用真实支付/提现、修改生产环境、直接改敏感集合、使用真实个人资料/凭据或改动无关 UI。

功能要求：主流程预约至评价；退款/超时；并发抢位、重复回调、越权、金额篡改、网络重试和通知失败；记录跨端状态一致性。

安全要求：角色隔离、请求 ID 追踪、最小日志、后端为事实来源、缺陷不泄露数据。

测试要求：每项写前置数据、操作端、预期订单/时段/支付/退款/日志状态、实际结果、证据和清理；阻断/高缺陷回归。

验收要求：主/异常流程可复现且跨端一致；无权限或资金副作用；未覆盖项透明记录。

报告要求：列出修改文件、剧本和结果、缺陷及根因、回归、风险和下一步；附 git diff 摘要，不要自行提交。
```

### 产出物

- 跨端联调数据包和主/异常剧本。
- 状态、日志、支付、退款、排期一致性证据表。
- 缺陷分级、根因与回归记录。

### 验收标准

- [ ] 同一虚构订单在三端和后端的状态/权限表现一致。
- [ ] 预约、支付模拟、确认、核销、完课、评价、退款和超时均有证据。
- [ ] 并发、重复、越权、篡改和网络重试无错误副作用。
- [ ] 阻断/高缺陷有修复回归或明确上线阻断结论。
- [ ] 全程未使用真实数据、支付、凭据或生产环境。

### 自查清单

- [ ] 已使用固定环境别名和可清理虚构数据。
- [ ] 每个步骤核对服务端状态，不只依赖 UI 截图。
- [ ] 异常测试使用正确角色和同一资源竞争。
- [ ] 未通过直接数据库修改“修复”测试状态。
- [ ] 联调报告已脱敏且列出未覆盖项。
