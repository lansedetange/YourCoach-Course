# 第 22 阶段：PC管理后台开发

### 本课目标

设计管理员在 PC 后台完成审核、运营配置、异常订单处置和审计查询的最小闭环，并把后台页面的能力限制在明确角色和受控后端动作之内。

### 你将完成

后台信息架构、权限矩阵、危险操作确认规则、列表筛选边界与虚构审核/异常处理验收记录。

### 前置条件

- 已完成用户、教练、场馆、排期和订单状态机设计。
- `admins` 集合和管理员鉴权接口已有受控定义。
- 已确认后台不是数据库控制台，所有修改仍通过云函数并写入审计记录。

### 核心概念

后台是高权限操作界面，不是“什么都能改”的页面。页面入口、按钮和路由守卫只改善体验；真正的权限由后端根据可信管理员身份、角色状态、对象范围和当前业务状态判断。高风险操作必须有明确目的、最小影响范围、二次确认和可追溯审计。

MVP 后台可分为：教练审核、项目/场馆/关联维护、订单异常查看、运营配置、管理员账号管理和审计查询。它不直接编辑支付原文、钱包余额、订单目标状态或生产数据库文档。

### 本课范围

本课设计后台 MVP，不实现完整 CRM、财务系统、批量导入、数据仓库、自动风控、任意 SQL 或跨城市运营。真实生产权限、值班机制和审批流程需由组织单独建立。

### 关键决策

- 管理员角色至少区分审核、运营、客服/异常处理和超级管理员；每个动作采用最小角色，不用一个通用 `admin` 权限覆盖全部。
- 所有列表以可筛选、分页、字段最小化为原则；不提供全量导出个人资料和敏感交易信息。
- 审核、上架、下架、订单异常、退款、配置变更均调用具名后端动作，携带原因/请求 ID 并写审计日志。
- 不可逆或高影响动作必须显示对象、影响、原因输入和二次确认；不能依靠浏览器弹窗作为唯一保护。

### 操作前检查

1. 将 `admins.role` 映射为页面路由和云函数权限，而不是只在前端隐藏菜单。
2. 列出每个后台模块的最小查询字段、可执行动作、必要理由和审计记录。
3. 准备虚构的待审核教练、下架场馆、异常订单和配置变更案例。
4. 确认列表数据脱敏：手机号、证件、支付标识和提现信息不默认显示或导出。

### 步骤 1

建立后台信息架构和角色矩阵。审核角色可处理教练申请与材料状态；运营角色可维护项目、场馆、教练-场馆关联和安全配置；异常处理角色可查看受限订单摘要并发起受控取消/退款流程；超级管理员仅负责管理员角色和高危配置。所有角色都可查看自身操作审计摘要。

前端路由守卫在进入模块前请求当前角色摘要；后端每个接口再次鉴权。预期：普通用户、教练或失效管理员即使构造 URL 或请求，也不能读取后台列表或执行管理动作。

### 步骤 2

为审核和供给维护页设计最小操作。待审列表只显示审核所需的脱敏资料，详情读取材料必须有审核权限；通过/驳回要求当前状态为待审，驳回原因采用分类和最小说明。项目、场馆、关联上架/下架显示对新订单和在途订单的影响，禁止物理删除历史关联对象。

配置页只允许维护 `system_configs` 白名单中的非敏感业务参数。密钥、证书、商户配置和环境变量不在页面显示、编辑或审计内容中；这类配置通过受控运维流程处理。

### 步骤 3

为订单异常页设计“查看—判断—发起受控动作”链路。管理员可按订单号（内部）、状态、时间和教练/用户受限标识筛选，并看到订单快照和日志摘要；不能在表格中直接改 `status`、金额或支付记录。取消、退款、核销纠正等操作必须进入状态机接口，填写分类原因并返回新的受控状态。

每次写操作产生审计事件：操作者、角色、动作、对象类型/ID、前后状态摘要、理由、请求 ID、时间和结果。审计日志只追加、限制读取，且不记录原始证件、支付凭据或完整个人资料。

### 步骤 4

使用虚构数据走读：审核员通过一位教练；运营员下架一个场馆；客服查看一笔异常订单并发起受控退款请求；普通用户访问后台被拒绝；重复提交审核动作被状态机拒绝；配置页拒绝未知键和敏感值。预期每项都由云函数返回结果，页面刷新后显示最新摘要。

检查批量操作、导出、删除按钮默认不存在或受严格限制。未完成真实权限、审计留存、监控告警和生产审批时，明确记录为上线前待办，不能由教学示例替代。

### 常见问题

- **隐藏菜单就认为安全：** 直接请求接口仍可能越权，后端授权才是边界。
- **管理员能任意改订单状态：** 必须通过状态机具名动作和审计，避免资金/履约数据失真。
- **配置页可见密钥：** 密钥不应进入业务后台页面或日志。
- **列表默认展示所有个人资料：** 仅显示当前操作需要的脱敏字段，导出需独立审批。
- **驳回后覆盖旧审核记录：** 审计追加新事件，历史不被静默覆盖。

### 安全与合规

后台实行最小权限、最小展示、二次确认和不可变审计。管理员角色从可信后端数据取得；所有敏感写入经云函数校验、记录并受状态机约束。不得在页面、课程、日志、截图或仓库中出现真实个人资料、交易、凭据、证书或生产配置。执行时请以微信公众平台当前页面和官方文档为准。

### Codex 提示词

```text
角色：你是资深运营后台、RBAC 权限与交易风控工程师，严格遵守项目根目录 AGENTS.md。

任务：在既有架构内完成 PC 管理后台 MVP 的页面和权限设计：审核、供给维护、订单异常、非敏感配置、管理员角色和审计。

上下文：YourCoach 有用户端、私教端和云开发后端。后台不直连数据库；订单、支付、退款、核销和余额由状态机与云函数处理。

允许范围：仅修改后台页面、组件、状态、必要共享类型和明确需要的文档/测试；复用既有鉴权和接口模式。

禁止范围：不得绕过后端权限、提供任意数据库编辑/导出、展示密钥证书、接入真实生产数据或重构无关 UI；不得输出个人信息、凭据或生产配置。

功能要求：定义审核、运营、异常处理、超级管理员的最小角色；提供分页筛选、受控审核/上下架/异常动作、原因和审计；危险操作有二次确认。

安全要求：后端 RBAC、对象范围与状态校验；最小字段展示；审计只追加；配置白名单；不让页面直接改订单、金额、支付、钱包或退款状态。

测试要求：用虚构数据验证角色路由、越权拒绝、审核幂等、场馆下架、受控退款请求、未知配置拒绝和审计记录；说明预期结果。

验收要求：所有管理操作有角色、原因、确认和审计；后台不泄露敏感资料或密钥；无直写敏感集合和未说明的假接口。

报告要求：列出修改文件、角色/操作决策、验证结果、未执行项、风险和下一步；附 git diff 摘要，不要自行提交。
```

### 产出物

- 后台信息架构与最小权限矩阵。
- 高风险操作确认和审计规则。
- 六类虚构后台验收案例。

### 验收标准

- [ ] 后台角色、路由、接口和对象范围均有最小权限定义。
- [ ] 审核、上下架、异常订单和配置动作经后端、理由、确认和审计。
- [ ] 订单/资金敏感状态不支持表格直改或任意数据库编辑。
- [ ] 列表、详情、导出均最小化展示敏感资料。
- [ ] 非管理员和越权管理员被后端拒绝。
- [ ] 未使用真实生产数据、凭据、个人资料或证书。

### 自查清单

- [ ] 未将前端菜单作为唯一权限控制。
- [ ] 未在后台保存或展示密钥、证书和支付原文。
- [ ] 每个写操作有对象、理由、结果和请求 ID 审计。
- [ ] 不可逆/高影响动作具有二次确认与状态机限制。
- [ ] 已检查测试数据、日志和 git diff 的脱敏。
