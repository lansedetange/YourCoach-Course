# 第 20 阶段：用户端小程序开发

### 本课目标

把已确认的产品、数据和订单契约映射为用户端最小页面闭环：浏览教练、查看详情、选择场馆与时段、发起预约、查看订单和安全展示状态。

### 你将完成

用户端页面清单、每页数据来源与权限边界、预约确认交互、加载/空态/错误态验收清单。

### 前置条件

- 已完成用户流程、页面地图、登录、供给侧、排期和订单状态机课程。
- `docs/API.md` 已定义受控查询和 `booking.create` 的响应语义。
- 已准备开发环境虚构教练、项目、场馆和可约时段。

### 核心概念

用户端是“展示可信服务信息并表达用户意图”的客户端，不是业务事实的裁判。教练是否上架、时段是否可约、最终价格、订单状态和支付结果都必须由后端返回；页面不能因为本地缓存或按钮状态而假定预约成功。

建议最小路径：首页/列表 → 教练详情 → 场馆与时段选择 → 预约确认 → 待支付/订单详情 → 我的订单。每个页面都应有加载、空态、可恢复错误和无权限状态，避免网络失败时展示过期或伪造的成功信息。

### 本课范围

本课设计用户端 MVP，不加入社交、团课、复杂筛选、地图导航、在线聊天、优惠券、多项目套餐或前端直连敏感集合。视觉样式遵循第 08 课原型，不借本课重构全部 UI。

### 关键决策

- 只展示已审核上线的教练、项目、场馆和已发布评价摘要。
- 预约确认必须选择有效场馆与可约时段；确认页展示后端返回或可核验的金额分格式，不由页面计算最终价格。
- 提交按钮以请求中的幂等键防连点；收到成功响应前不乐观写入订单列表。
- 订单按钮由后端状态驱动，例如待支付可支付/取消、待确认显示等待、已完成可评价；无合法动作时不显示伪操作。

### 操作前检查

1. 对照 `docs/PAGE_MAP.md`、`docs/USER_FLOWS.md` 与 `docs/ORDER_STATE.md` 列出本课页面和合法动作。
2. 明确每个页面的最小接口、加载状态、空态文本、错误码映射和返回入口。
3. 确认列表不请求证书、内部审核意见、钱包、支付原文或其他用户数据。
4. 准备一个可约和一个不可约的虚构教练场景。

### 步骤 1

实现/设计列表与详情的数据边界。列表只读取已上线教练的头像占位、展示名、主项目、价格起点和服务场馆摘要；详情页读取公开简介、有效场馆、可约时段和已发布评价。进入详情时重新加载关键可约数据，不把上一个用户的缓存当作当前事实。

列表为空时明确提示当前城市暂无可预约教练；加载失败时提供重试，不显示编造的推荐。预期结果是下架教练、失效场馆和审核材料均不会进入用户端视图。

### 步骤 2

设计预约确认页：用户选择场馆和时段后，页面展示教练、项目、场馆、开始时间、时长和待确认金额；提交只传候选 ID 与幂等键给 `booking.create`。后端若返回 `CONFLICT_SLOT_UNAVAILABLE`，页面提示时段已被占用并刷新可约列表；不得保留一个本地“成功订单”。

提交过程中禁用重复触发并保留可见进度；网络超时提示用户到订单列表刷新确认，而不是自动重复创建。后端成功返回 `PENDING_PAYMENT` 后，再跳转订单详情或待支付页。

### 步骤 3

订单列表按本人归属读取，并按状态分组/筛选。订单详情使用交易快照展示，不因项目或场馆资料更新而跳变。支付、取消、评价等按钮仅在接口允许的状态出现；点击后调用具名后端动作，等待返回的订单摘要刷新页面。

对 `AUTH_REQUIRED` 引导重新登录，对 `FORBIDDEN/NOT_FOUND` 显示安全通用提示，不泄露订单归属；对 `PAYMENT_PENDING` 展示处理中并提供刷新；对不可恢复错误记录脱敏诊断信息。不要将后台错误堆栈直接弹给用户。

### 步骤 4

用虚构数据完成走查：首页列表、教练详情、选择场馆时段、成功创建待支付订单、同一时段冲突、订单状态刷新。预期：每一步有加载与错误反馈；冲突不产生第二笔有效订单；订单列表只显示当前用户订单；刷新后状态以服务端为准。

在真机或开发者工具中检查授权拒绝、网络断开、空列表和重复点击。记录未完成的真实支付、地图、订阅通知验证，后续课程单独覆盖。

### 常见问题

- **页面自己把订单改为已支付：** 支付结果只能由可信后端更新。
- **不选场馆即可提交：** MVP 下单必须选有效场馆，前后端均校验。
- **缓存时段直接下单：** 提交前必须让后端重查；冲突后刷新。
- **把所有接口错误原样展示：** 只映射稳定错误码，内部细节留在脱敏日志。
- **列表显示审核材料：** 用户端只读公开字段。

### 安全与合规

客户端不保存或打印敏感身份、支付、证书、后台审核和钱包数据；网络请求最小化，页面不信任本地角色、金额、状态或用户 ID。用户端任何敏感动作均通过云函数。执行时请以微信公众平台当前页面和官方文档为准。

### Codex 提示词

```text
角色：你是资深微信小程序前端与预约产品工程师，严格遵守项目根目录 AGENTS.md。

任务：在既有架构与视觉规范内完成用户端 MVP 页面闭环：浏览、详情、场馆时段选择、预约确认、订单列表和状态展示。

上下文：订单、价格、时段和状态均由后端状态机决定；用户必须选择有效场馆；同一教练同一时段只能有一个有效订单。

允许范围：仅修改用户端页面、组件、状态和明确需要的文档/测试；复用现有接口与样式模式。

禁止范围：不得前端直写订单/支付/退款/排期；不得接入真实支付、地图、聊天或无关 UI 重构；不得输出真实个人数据、凭据或生产配置。

功能要求：实现加载、空态、错误态；预约提交带幂等保护；根据后端错误码处理冲突；订单页面仅展示本人交易快照与合法动作。

安全要求：不信任客户端金额、角色、状态和身份；最小展示公开字段；不暴露审核材料或内部错误；日志脱敏。

测试要求：用虚构数据验证浏览、预约成功、时段冲突、重复点击、订单刷新、登录失效和网络失败；说明操作和预期结果。

验收要求：用户必须选择有效场馆/时段；成功前不乐观创建订单；冲突不产生第二笔订单；无敏感字段或秘密信息泄露。

报告要求：列出修改文件、页面与状态决策、验证结果、未执行项、风险与下一步；附 git diff 摘要，不要自行提交。
```

### 验收标准

- [ ] 用户仅能看到已上线公开服务信息和自己的订单。
- [ ] 预约必须选择有效场馆、时段，提交由后端确认。
- [ ] 加载、空态、网络失败、登录失效和冲突均有安全反馈。
- [ ] 订单按钮只映射合法后端动作，状态刷新以服务端为准。
- [ ] 未暴露证书、审核、钱包、支付原文、凭据或真实数据。

### 自查清单

- [ ] 未把缓存、页面角色或按钮状态当作权限依据。
- [ ] 未让页面计算最终金额或直接改订单状态。
- [ ] 重复点击和网络超时不会重复创建订单。
- [ ] 已检查小程序端日志和请求样例脱敏。
- [ ] 未扩展地图、聊天、团课等范围外功能。
